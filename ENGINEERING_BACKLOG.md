# Operant — Living Engineering Backlog

**Updated:** 2026-10-08  
**Operating principle:** A passing test suite is evidence for tested cases, not proof that the architecture is optimal. Re-rank this backlog after each material implementation and keep design assumptions explicit.

## Current architecture decision: temporal provider snapshots

**Status:** Temporal provider selection, completeness gates, jittered retries, conservative conflict refresh, GitHub payload minimization with legacy-row compatibility, batched action-conflict evaluation, and historical resource-version selection are implemented. Latest full validation on 2026-10-08: **63 passed; 3 opt-in MySQL tests skipped**; TypeScript check, build, Drizzle journal check, and `git diff --check` pass. Fresh local production entrypoint checks returned HTTP 200 for health and readiness and listed nine routes; DB/schema probes were healthy. `activeRetryScheduleRegistered: false` remains an explicit unresolved production activation gate. The build emits the existing non-fatal Vite notice for runtime-loaded `/api/platform/config.js`.

GitHub issue observations are snapshots from an upstream system. Their effective time (`validFrom`, sourced from GitHub `updatedAt`) differs from their arrival/record time (`recordedAt`). They must not be chained as retroactive corrections merely because one webhook was processed later. Provider snapshots are grouped by entity, attribute, provider, and connection; the current belief is selected by valid time after filtering to observations recorded by the requested knowledge cutoff. Legacy GitHub supersession links within the same stream are interpreted as version history. Explicit corrections across streams remain superseding decisions, and separate provider connections remain independent sources.

### Resource-version history decision

The World Model now uses a pure shared selector: a version remains effective before a known successor's `validFrom`, ends at that half-open transition, and is selected only if it was recorded by the requested knowledge cutoff. Explicit `validTo` bounds, chained updates, and conflicting successor branches are preserved. The schema and database were not changed. A malformed interval or cross-resource supersession link cannot rewrite a valid predecessor in the selector.

Alternatives considered: (1) patch only the World Model route, risking a second temporal implementation; (2) selected shared pure projection, with no migration and regression coverage; (3) move to a normalized append-only temporal ledger with explicit temporal modes, which remains the strongest long-term model but needs migration and backfill design. Still unresolved: whether zero-length `[t,t)` versions have product meaning, and how the API should visibly flag corrupt historical rows rather than merely excluding them.

### Provider temporal research notes

- [Martin Fowler, “Bitemporal History”](https://martinfowler.com/articles/bitemporal-history.html) distinguishes actual/valid history from record/transaction history.
- [XTDB, “Bitemporality”](https://v1-docs.xtdb.com/concepts/bitemporality/) discusses out-of-order valid-time values and transaction-time history.
- [Halawa & Ripeanu, “Position paper: bitemporal dynamic graph analytics” (ACM SIGMOD workshop, 2021)](https://doi.org/10.1145/3461837.3464514) treats historical investigation and stale-data decisions as first-class requirements.
- [AWS Architecture Blog, “Exponential Backoff and Jitter”](https://aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter/) explains how jitter avoids synchronized retry clusters.
- [Amazon Builders’ Library, “Timeouts, retries, and backoff with jitter”](https://builder.aws.com/content/3EumjoZascWd1oZiEgL8ORlv3qE/timeouts-retries-and-backoff-with-jitter) emphasizes bounded retry and retry-amplification safeguards.
- [Google Cloud Storage retry strategy](https://docs.cloud.google.com/storage/docs/retry-strategy) recommends backoff with jitter for eligible idempotent operations and finite limits.

## Operating loop

After each major implementation: (1) add a regression test for the discovered failure mode, (2) run targeted and full checks, (3) revise priorities based on new evidence, (4) record the next chosen design and unresolved gates here. Do not call the platform “finished” solely because current checks pass.
